在我们制定的升级计划中，Ocelot API 网关的升级是唯一一个被标记为高风险的步骤。这并不难理解，Ocelot 承担着整个系统唯一对外入口的职责，所有来自客户端的请求都必须先经过网关的路由分发、身份认证与流量转发，才能到达各个下游微服务。一旦网关在升级后出现异常或配置错误，整个系统对外来说就等同于不可用。因此对于这一步骤，简单地修改版本号远远不够，我们还需要仔细研读版本之间引入的每一项变更，逐一确认路由规则、认证集成与服务配置在升级后依然能够正常工作。

### 一、升级前的准备工作
任何包升级的第一步，都是确认目标版本。我们打开 NuGet.org 搜索 Ocelot 包，可以看到截至本文撰写时，最新的稳定版本是 **24.1.0**，于 2025 年 12 月正式发布，支持 `net8.0` 和 `net9.0` 两个目标框架。与此同时，Ocelot 团队也在同步推进 .NET 10 的原生支持，目前已有 **25.0.0-beta.2** 发布于 2026 年 3 月，该版本基于 .NET SDK 10.0.201 构建，是第一个以 `net10.0` 为原生目标框架的 Ocelot 版本，Ocelot 官方团队在发布说明中明确表示："开发团队现在可以使用这个 Beta 2 版本开始将 Ocelot 项目迁移到 .NET 10 SDK"。

面对这两个候选版本，我们需要做出一个版本决策。选择 24.1.0 稳定版的好处是零风险——它是正式发布版本，.NET 10 对 `net9.0` 的向下兼容性也足以保证其正常运行。然而，这条路意味着我们必须接受一次"两步走"的升级节奏：先用 24.1.0 完成当前的 .NET 10 迁移，等 25.0.0 正式版发布后再做一次单独的 Ocelot 升级。更重要的是，24.1.0 在其 File-model 配置模型中新增了大量 `[Obsolete]` 标注，这些弃用的 API 将在 25.0.0 中彻底移除，变成编译错误——如果我们的项目恰好使用了这些 API，那么推迟处理只会让未来的升级更加被动。

综合考量后，我们选择直接升级到 **25.0.0-beta.2**，理由有三：第一，它提供了与项目其他组件一致的 `net10.0` 原生 TFM，技术栈对齐更彻底；第二，Ocelot 团队官方推荐用这个版本进行 .NET 10 迁移，说明其稳定性已经过基本验证；第三，孢子记账的 Gateway 层并未使用 Kubernetes 或 Eureka 服务发现，而这两个扩展包是 beta.2 发布说明中唯一标注"仍在开发中，存在不稳定风险"的部分，对我们的项目实际上不构成任何影响。

> Tip：评估预发布版本是否可用于当前项目的关键，不是看"是否 beta"，而是看"不稳定的部分是否是我们实际使用的部分"。25.0.0-beta.2 中核心路由、认证、请求转发等功能均已稳定，唯一的不稳定项（PollKube 服务发现）与孢子记账无关，因此采用它是合理的。

确定目标版本后，我们还需要在动手之前弄清楚从 24.0.1 升级到 25.0.0-beta.2 这个跨度内引入了哪些变化。最关键的破坏性变更来自 25.0.0 对 24.1.0 中弃用清单的执行，24.1.0 用 `[Obsolete]` 标注的一批 File-model 配置属性，在 25.0.0 中已被正式移除。这意味着如果 `Program.cs` 的 Ocelot 服务注册链中使用了这些属性，升级后会直接产生 `CS0619` 编译错误而非警告，必须在构建通过之前完成修复。24.1.0 引入的"路由默认超时（Routing default timeout）"特性在 25.0.0 中同样保留，这是一个可选的增量特性，不会对现有配置造成破坏。

### 二、升级
#### 2.1 升级 NuGet 包
由于 25.0.0-beta.2 是预发布版本，直接执行 `dotnet add package Ocelot` 不会自动获取它，需要通过显式版本号来指定。这一步改动非常单一，直接以 Agent 模式提交给 AI 执行即可，无需启动 Plan 模式：

```markdown
请将 SP.Gateway 项目中的 Ocelot 包从 24.0.1 升级到 25.0.0-beta.2，执行命令时需要通过显式版本号指定预发布版本。完成后执行 `dotnet build`，将完整的构建输出返回给我，重点关注是否存在 CS0619 编译错误。
```

AI 的输出如下图所示，成功完成版本替换并执行了构建，构建结果显示零错误，说明现有代码路径未触及任何已被移除的 API，可以直接进入下一步。完成包替换后，AI 会执行 `dotnet build` 并将输出返回。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/93066f90e1a8468a895e5ff92cee48f1.png)

这里需要重点关注的是 `CS0619` 错误——与 `CS0618`（警告）不同，`CS0619` 表示代码引用了已经被彻底移除的 API，是阻断编译的硬错误。一条典型的 CS0619 错误会是这样的形式：

```
error CS0619: 'FileRoute.SomeRemovedProperty' is obsolete:
'This property was removed in v25.0.0. Use NewProperty instead.'
```

如果出现此类错误，将错误信息直接粘贴给 AI，让它根据错误中给出的替代 API 说明完成逐一修复。孢子记账 Gateway 项目在完成版本替换并执行 `dotnet build` 后，构建结果显示零错误，说明现有代码路径未触及任何已被移除的 API，可以直接进入下一步。

#### 2.2 生成新的 ocelot.json 路由配置
在孢子记账项目中，`ocelot.json` 并不存放在代码仓库里，而是托管在 Nacos 配置中心，由网关启动时动态拉取，我们无法通过 `dotnet build` 或代码审查来发现配置问题，必须主动生成一份符合 25.0.0-beta.2 规范的新配置，然后更新到 Nacos 中。这一步非常适合以 Agent 模式交给 AI 来完成——AI 可以读取项目中所有的Web API 接口，结合版本变更说明，直接产出一份可以上传到 Nacos 的完整 JSON：

```markdown
请对照 Ocelot 25.0.0-beta.2 的变更说明，基于孢子记账项目现有的Web API 接口，生成一份符合新版本规范的完整 ocelot.json 配置文件。要求：
1. 移除所有在 25.0.0-beta.2 中已被删除的弃用字段；
2. 评估 GlobalConfiguration 是否适合新增默认超时配置，如果适合请添加一个 Timeout 字段，单位为毫秒，默认值为 30000；
3. 输出完整的 JSON 内容，不要省略任何路由条目。
```

AI 生成的配置结构大致如下，`GlobalConfiguration` 新增了 `Timeout` 字段，各路由条目保持原有结构不变：

```json
{
  "GlobalConfiguration": {
    "BaseUrl": "https://api.spore.com",
    "Timeout": 30000
  },
  "Routes": [
    {
      "UpstreamPathTemplate": "/api/finance/{everything}",
      "UpstreamHttpMethod": [ "GET", "POST", "PUT", "DELETE" ],
      "DownstreamPathTemplate": "/api/finance/{everything}",
      "DownstreamScheme": "http",
      "DownstreamHostAndPorts": [
        { "Host": "sp-financeservice", "Port": 80 }
      ],
      "AuthenticationOptions": {
        "AuthenticationProviderKey": "Bearer"
      }
    }
    // ... 其余路由条目
  ]
}
```

> Tip：`Timeout` 的单位是毫秒。`GlobalConfiguration` 层级的值作为所有路由的默认超时，单条路由上配置的 `Timeout` 会覆盖全局默认值。Nacos 中存储的是完整的 JSON 文本，直接将 AI 生成的内容粘贴替换即可，无需重启 Nacos 服务，网关下次启动或热更新时会自动拉取新配置。

拿到 AI 生成的完整配置后，将其更新到 Nacos 配置中心对应的 DataId 中。完成后在本地启动网关服务，通过网关向下游微服务发送几条请求，确认路由转发、Bearer Token 验证和响应回传均正常，本次升级即告完成。

### 三、总结
本次 Ocelot 升级从表面上看是一次版本号的变更，背后却包含了若干需要主动判断的决策点。在版本选择上，我们放弃了"稳妥"的 24.1.0 稳定版，转而采用 Ocelot 官方推荐用于 .NET 10 迁移的 **25.0.0-beta.2** 预发布版，从而一步到位地实现了 `net10.0` 的原生 TFM 对齐，避免了未来再做一次单独升级的额外成本。在风险把控上，通过识别 beta 版本中真正不稳定的部分（Kubernetes PollKube 服务发现）与项目实际使用的功能之间的重叠情况，可以得出"对我们而言风险可控"的结论，这比笼统地"因为是 beta 就不用"或"因为官方推荐就直接上"都更为严谨。在破坏性变更上，25.0.0-beta.2 将 24.1.0 中的 `[Obsolete]` 属性彻底移除，需要重点排查 `CS0619` 编译错误，而 AI Coding 在这里发挥了显著的效率提升作用——它不仅能快速定位错误，还能根据官方迁移说明给出对应的替代写法。
