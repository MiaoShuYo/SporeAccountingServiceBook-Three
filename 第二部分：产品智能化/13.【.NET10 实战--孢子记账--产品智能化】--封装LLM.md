在前两篇文章中，我们完成了孢子记账智能化改造的两项关键前置工作：先是横向对比了当前主流的 LLM 平台，确定了以硅基流动（SiliconFlow）作为项目的模型推理底座；随后又在 .NET 生态中评估了官方 SDK、第三方封装库与直接调用 HTTP API 三种接入方式，最终选择了 OpenAI 官方 SDK 作为技术实现路径。至此，"用谁的模型"和"怎么用"这两个方向性问题都有了明确的答案。

然而，方向确定只是第一步。当我们真正开始将大模型能力融入孢子记账的各个微服务时，一个现实问题立刻浮现，如果每个微服务都各自创建 `OpenAIClient` 实例、各自管理 API Key、各自处理异常与重试逻辑，整个系统很快就会陷入配置分散、代码重复、维护困难的泥潭。孢子记账目前包含多个微服务，智能化改造意味着它们都可能在不同的业务场景下需要调用大模型能力。在这样的微服务架构中，将大模型调用能力抽象为一个统一、可复用的基础组件，几乎是工程上的必然选择。

### 一、封装 LLM 调用层的必要性
封装 LLM 调用层的核心目标是将与大模型交互的复杂性集中管理，提供一个简洁、稳定、易用的接口供各个微服务调用。通过封装，我们可以实现以下几个方面的价值：

- **统一配置**：将硅基流动的 API Key、Base URL、默认模型等配置集中管理，避免在每个微服务中重复散落；
- **服务注册**：与 .NET 的依赖注入体系无缝集成，让任何微服务只需一行 `builder.Services.AddOpenAIService(...)` 即可获得大模型调用能力；
- **异常处理与容错**：封装层的调用不应因为一次网络抖动就导致业务直接失败，需要内置合理的重试与降级策略；
- **日志与可观测性**：在调用链中埋入必要的日志与追踪信息，便于后续排查问题与监控调用成本；
- **通用性与扩展性**：封装后的组件既要满足当前的对话补全（Chat Completion）需求，也要为后续可能引入的嵌入（Embedding）、函数调用（Function Calling）等能力留出扩展空间。

在当前阶段，孢子记账的智能化改造主要聚焦在对话补全能力的接入，因此我们将以此为核心功能进行封装设计。但从长远来看，我们还是希望在这个组件的基础上进一步封装其他大模型能力，如嵌入（Embedding）、函数调用（Function Calling）以及计费功能等，以满足未来更多业务场景的需求。

在设计封装层之前，我们先来审视一下如果不做封装，各个微服务直接调用 OpenAI SDK 会是什么样子。假设服务需要调用大模型来实现智能账单分类，它可能会写出类似下面这样的代码：

```csharp
// ❌ 反模式：每个微服务都直接创建 OpenAIClient
public class BillClassificationService
{
    public async Task<string> ClassifyBillAsync(string description)
    {
        var client = new OpenAIClient(
            new ApiKeyCredential("sk-xxxxxxxxxxxx"),
            new OpenAIClientOptions
            {
                Endpoint = new Uri("https://api.siliconflow.cn/v1")
            });

        var chatClient = client.GetChatClient("deepseek-ai/DeepSeek-V3");
        var completion = await chatClient.CompleteChatAsync(
            $"请将以下消费描述分类：{description}");

        return completion.Content[0].Text;
    }
}
```

这段代码乍看之下能跑通，但细看就会发现一系列工程隐患。API Key 硬编码在业务代码中，一旦需要轮换就得全局搜索替换，`OpenAIClient` 的创建散落在各个类中，无法统一管理连接池和生命周期。没有任何异常处理，网络一抖业务就直接抛异常。缺少日志，出了问题无从排查是哪次调用、哪个模型、耗时多久。当这样的代码在账单服务、预算服务、报表服务、用户服务中各自复制一份时，维护成本会以服务数量的倍数增长。

因此我们需要在 OpenAI SDK 之上构建一个薄封装层，它的本质是一个"门面"（Facade）。对外暴露简洁的、面向业务语义的接口，对内管理 `OpenAIClient` 的创建、配置、生命周期以及所有横切关注点（日志、异常、重试）。每个微服务只需要注入一个接口，调用一个方法，其余的事情全部由封装层代劳。

### 二、设计目标与核心功能
明确了封装的必要性之后，我们需要将目标进一步具体化，梳理出封装层应当具备的核心能力。

#### 2.1 接口设计：面向业务而非面向 SDK
封装层的第一原则是，**对外暴露的接口应当反映业务需求，而非直接照搬 SDK 的 API**。如果封装后的接口仍然是 `CompleteChatAsync(List<ChatMessage> messages)`，那不过是在 OpenAI SDK 外面套了一层薄壳，并没有降低调用方的理解成本。

我们希望各个微服务的业务代码在调用时，关注的是"我要问模型什么问题"以及"模型返回了什么答案"，而不需要关心 `ChatMessage` 的角色枚举、`ChatCompletionOptions` 的参数细节或是流式响应的遍历方式。因此，我们设计了如下 `IOpenAIService` 接口：

```csharp
public interface IOpenAIService
{
    /// <summary>
    /// 发送单条用户消息，返回完整回复
    /// </summary>
    Task<string> ChatAsync(string message, CancellationToken cancellationToken = default);

    /// <summary>
    /// 发送多轮对话消息，返回完整回复
    /// </summary>
    Task<string> ChatAsync(IEnumerable<ChatMessage> messages, CancellationToken cancellationToken = default);

    /// <summary>
    /// 发送单条用户消息，以流式方式逐块返回回复
    /// </summary>
    IAsyncEnumerable<string> ChatStreamingAsync(string message, CancellationToken cancellationToken = default);

    /// <summary>
    /// 发送多轮对话消息，以流式方式逐块返回回复
    /// </summary>
    IAsyncEnumerable<string> ChatStreamingAsync(IEnumerable<ChatMessage> messages, CancellationToken cancellationToken = default);
}
```

这个接口的设计有几个值得注意的细节。首先，接口同时提供了 `string message` 和 `IEnumerable<ChatMessage>` 两个重载，前者覆盖 80% 以上"一句话提问"的简单场景，调用方无需手动构造 `ChatMessage` 对象，后者则满足需要携带 system prompt 或历史对话上下文的复杂场景，两者互为补充，兼顾了简洁性与灵活性。其次非流式与流式被设计为独立方法，而非用一个 `bool` 参数切换，这使得返回值类型更加明确（`Task<string>` vs `IAsyncEnumerable<string>`），调用方看到方法签名就能理解其行为，不会产生歧义。最后所有异步方法均接受 `CancellationToken`，遵循 .NET 异步编程的最佳实践，确保请求可以通过取消令牌优雅中止，而不会因为一个已被用户取消的操作仍在等待模型返回而白白消耗资源。

#### 2.2 配置模型：单一入口，合理默认值
封装层需要一套结构化的配置模型来承载硅基流动的连接信息与容错参数。我们将配置建模为 `OpenAIOptions` 类：

```csharp
public class OpenAIOptions
{
    /// <summary>API 密钥</summary>
    public string ApiKey { get; set; } = string.Empty;

    /// <summary>API 基础 URL，默认 https://api.openai.com/v1</summary>
    public string ApiSecret { get; set; } = "https://api.openai.com/v1";

    /// <summary>模型名称</summary>
    public string Model { get; set; } = string.Empty;

    /// <summary>最大重试次数（仅针对可重试的瞬态错误），默认 3</summary>
    public int MaxRetries { get; set; } = 3;

    /// <summary>首次重试基础延迟（毫秒），之后按指数增长，默认 500</summary>
    public int RetryDelayMilliseconds { get; set; } = 500;
}
```

这里有两个字段名需要特别说明，`ApiSecret` 在项目中实际上承载的是 **API 基础 URL**（而非密钥），这是历史命名留下的痕迹，读者在实际项目中可以根据自己的习惯将其重命名为 `BaseUrl` 或 `Endpoint`。`Model` 字段指定默认使用的模型名称，例如硅基流动平台上的 `deepseek-ai/DeepSeek-V3` 或 `Qwen/Qwen2.5-7B-Instruct`。

除了连接信息之外，`OpenAIOptions` 还内置了容错参数。`MaxRetries` 控制最大重试次数，`RetryDelayMilliseconds` 则定义了指数退避的基准延迟。这两个参数使得调用方可以根据自身对可用性的要求灵活调整重试策略，而不需要修改封装层代码。

在 Nacos 中，对应的配置节点如下：

```json
{
  "OpenAI": {
    "ApiKey": "sk-xxxxxxxxxxxx",
    "ApiSecret": "https://api.siliconflow.cn/v1",
    "Model": "deepseek-ai/DeepSeek-V3",
    "MaxRetries": 3,
    "RetryDelayMilliseconds": 500
  }
}
```

#### 2.3 核心能力：重试与指数退避
在分布式系统中调用第三方 API，网络抖动、服务端限流（HTTP 429）、临时性服务端错误（HTTP 5xx）都是不可避免的。封装层必须在这些场景下具备自愈能力，而不是把原始异常直接抛给上层业务代码。

我们在这层封装中内置了一套**指数退避重试机制**，其核心逻辑可以从三个维度来理解。在错误判定上，并非所有异常都值得重试，只有 HTTP `429`（限流）和 `5xx`（服务端临时错误）才被认定为可重试的瞬态错误，`401` 鉴权失败、`400` 参数错误等明确的客户端问题会直接抛出，避免白白消耗重试次数。在延迟策略上，采用指数退避而非固定间隔：第 n 次重试的等待时间为 `RetryDelayMilliseconds × 2^(n-1)`，以默认的 500ms 基准为例，三次重试的等待依次为 500ms、1000ms、2000ms，越晚的重试等待越久，给服务端更多恢复时间，同时也避免了大量请求同时重试时形成的"重试风暴"。在取消响应上，重试等待期间同样将 `CancellationToken` 传入 `Task.Delay`，确保上游一旦发出取消信号，等待立即中止，不会因为正在退避就无法响应用户的取消操作。

对于流式调用，重试的处理稍有不同。因为流式响应在 HTTP 连接建立后就开始逐块传输数据，如果在传输中途发生错误，已输出的文本块已经发送给了调用方，无法"撤回"。因此，流式重试的策略是**先缓冲全部响应，再逐块输出**：在内部用 `CollectStreamWithRetryAsync` 方法收集所有文本块到一个 `List<string>` 中，确认完整成功后再逐个 `yield return`。这种策略牺牲了少量的首字节延迟，换取了重试语义的正确性——调用方要么拿到完整的响应，要么在重试耗尽后收到异常，不会出现"前半段来自第一次调用、后半段来自重试调用"的混乱情况。

#### 3.5 第五步：实现 OpenAIService（含重试与指数退避）
这是封装层最核心的部分。`OpenAIService` 实现了 `IOpenAIService` 接口，并内置了日志记录、异常分类处理以及指数退避重试机制。完整代码如下：

```csharp
public class OpenAIService : IOpenAIService
{
    private readonly ChatClient _chatClient;
    private readonly ILogger<OpenAIService> _logger;
    private readonly int _maxRetries;
    private readonly int _retryDelayMs;

    public OpenAIService(OpenAIOptions options, ILogger<OpenAIService> logger)
    {
        _logger = logger;
        _maxRetries = Math.Max(1, options.MaxRetries);
        _retryDelayMs = Math.Max(0, options.RetryDelayMilliseconds);

        var endpoint = new Uri(options.ApiSecret);
        var credential = new ApiKeyCredential(options.ApiKey);
        var clientOptions = new OpenAIClientOptions { Endpoint = endpoint };
        _chatClient = new OpenAIClient(credential, clientOptions).GetChatClient(options.Model);
    }

    public Task<string> ChatAsync(string message, CancellationToken cancellationToken = default)
        => ChatAsync([ChatMessage.CreateUserMessage(message)], cancellationToken);

    public async Task<string> ChatAsync(IEnumerable<ChatMessage> messages, CancellationToken cancellationToken = default)
    {
        IList<ChatMessage> messageList = messages as IList<ChatMessage> ?? messages.ToList();
        _logger.LogDebug("[OpenAI] ChatAsync 开始，消息数：{Count}", messageList.Count);

        for (int attempt = 1; attempt <= _maxRetries; attempt++)
        {
            try
            {
                ClientResult<ChatCompletion> result =
                    await _chatClient.CompleteChatAsync(messageList, cancellationToken: cancellationToken);

                string text = result.Value.Content[0].Text;
                _logger.LogDebug("[OpenAI] ChatAsync 成功，Token 用量：{Tokens}",
                    result.Value.Usage?.TotalTokenCount);
                return text;
            }
            catch (ClientResultException ex) when (IsTransient(ex) && attempt < _maxRetries)
            {
                int delay = CalculateDelay(attempt);
                _logger.LogWarning(ex,
                    "[OpenAI] ChatAsync 瞬态错误（HTTP {Status}），第 {Attempt}/{Max} 次，{Delay}ms 后重试",
                    ex.Status, attempt, _maxRetries, delay);
                await Task.Delay(delay, cancellationToken);
            }
            catch (OperationCanceledException)
            {
                _logger.LogInformation("[OpenAI] ChatAsync 已取消");
                throw;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "[OpenAI] ChatAsync 不可重试的错误（第 {Attempt} 次尝试）", attempt);
                throw;
            }
        }

        _logger.LogError("[OpenAI] ChatAsync 已达最大重试次数 {Max}", _maxRetries);
        throw new InvalidOperationException($"OpenAI ChatAsync 超出最大重试次数（{_maxRetries}）。");
    }
}
```

这段实现有几个关键设计值得展开说明。首先是 `ChatClient` 的创建时机。OpenAI SDK 推荐复用 `OpenAIClient` 实例以利用底层 HTTP 连接池，而 `ChatClient` 是一个轻量级包装，在构造时绑定模型名称后同样可以安全复用。将 `_chatClient` 作为实例字段在构造函数中一次性初始化，避免了每次 `ChatAsync` 调用时重复创建对象的开销。

其次是异常的分类处理。`catch` 块针对三种不同性质的异常分别应对。当捕获到 `ClientResultException` 且属于瞬态错误、且尚未达到最大重试次数时，记录警告日志并等待退避后继续重试。当捕获到 `OperationCanceledException` 时，记录信息日志后直接重新抛出，取消是调用方的主动行为，不是错误，不应触发重试。对于其他所有异常，记录错误日志后立即抛出，因为这类错误（鉴权失败、参数错误等）无论重试多少次结果都不会改变。

瞬态错误的判定逻辑如下，只有 HTTP `429`（限流）和 `5xx`（服务端临时错误）才被认定为值得重试的瞬态错误，这是与大模型 API 交互的业界通用做法：

```csharp
private static bool IsTransient(ClientResultException ex)
    => ex.Status == 429 || (ex.Status >= 500 && ex.Status <= 599);
```

退避延迟则按指数增长，第 n 次重试的等待时间由以下方法计算，以默认的 500ms 为基准，三次重试的等待依次为 500ms、1000ms、2000ms，越晚的重试等待越久，避免了大量请求同时重试时形成的"重试风暴"：

```csharp
private int CalculateDelay(int attempt)
    => _retryDelayMs * (int)Math.Pow(2, attempt - 1);
```

#### 3.6 第六步：流式调用的实现
流式调用 `ChatStreamingAsync` 的实现与非流式有本质区别。由于流式响应是在 HTTP 连接建立后逐步传输的，如果中途出错，已发送给调用方的数据块无法"撤回"。为了确保重试语义的正确性，我们采用"先收集再输出"的策略：

```csharp
public IAsyncEnumerable<string> ChatStreamingAsync(string message, CancellationToken cancellationToken = default)
    => ChatStreamingAsync([ChatMessage.CreateUserMessage(message)], cancellationToken);

public async IAsyncEnumerable<string> ChatStreamingAsync(
    IEnumerable<ChatMessage> messages,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    IList<ChatMessage> messageList = messages as IList<ChatMessage> ?? messages.ToList();
    _logger.LogDebug("[OpenAI] ChatStreamingAsync 开始，消息数：{Count}", messageList.Count);

    List<string> chunks = await CollectStreamWithRetryAsync(messageList, cancellationToken);

    foreach (string chunk in chunks)
        yield return chunk;
}
```

核心逻辑委托给私有方法 `CollectStreamWithRetryAsync`，它在内部用与 `ChatAsync` 相同的重试循环收集所有文本块：

```csharp
private async Task<List<string>> CollectStreamWithRetryAsync(
    IList<ChatMessage> messages, CancellationToken cancellationToken)
{
    for (int attempt = 1; attempt <= _maxRetries; attempt++)
    {
        try
        {
            var chunks = new List<string>();
            AsyncCollectionResult<StreamingChatCompletionUpdate> stream =
                _chatClient.CompleteChatStreamingAsync(messages, cancellationToken: cancellationToken);

            await foreach (StreamingChatCompletionUpdate update in stream.WithCancellation(cancellationToken))
            {
                foreach (ChatMessageContentPart part in update.ContentUpdate)
                {
                    if (!string.IsNullOrEmpty(part.Text))
                        chunks.Add(part.Text);
                }
            }

            _logger.LogDebug("[OpenAI] ChatStreamingAsync 成功，共 {Count} 个文本块", chunks.Count);
            return chunks;
        }
        catch (ClientResultException ex) when (IsTransient(ex) && attempt < _maxRetries)
        {
            int delay = CalculateDelay(attempt);
            _logger.LogWarning(ex,
                "[OpenAI] ChatStreamingAsync 瞬态错误（HTTP {Status}），第 {Attempt}/{Max} 次，{Delay}ms 后重试",
                ex.Status, attempt, _maxRetries, delay);
            await Task.Delay(delay, cancellationToken);
        }
        catch (OperationCanceledException)
        {
            _logger.LogInformation("[OpenAI] ChatStreamingAsync 已取消");
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "[OpenAI] ChatStreamingAsync 不可重试的错误（第 {Attempt} 次尝试）", attempt);
            throw;
        }
    }

    _logger.LogError("[OpenAI] ChatStreamingAsync 已达最大重试次数 {Max}", _maxRetries);
    throw new InvalidOperationException($"OpenAI ChatStreamingAsync 超出最大重试次数（{_maxRetries}）。");
}
```

这种"缓冲后输出"的策略有一个取舍。调用方不会在第一个文本块到达时立即收到它，而是需要等待整个流式响应完成。对于孢子记账的场景（智能分类、趋势分析等），单次调用的响应内容通常较短（几十到几百字），这个延迟可以忽略不计。如果未来遇到需要极低首字节延迟的场景，可以将缓冲策略替换为"直接透传 + 失败后通知调用方自行重试"的模式，该扩展点已在接口设计中预留。

#### 3.7 第七步：注册到 DI 容器
最后，我们需要提供一个扩展方法将上述组件串联起来并注册到依赖注入容器。这是整个封装层的"入口"：

```csharp
public static class OpenAIServiceExtensions
{
    public static IServiceCollection AddOpenAIService(this IServiceCollection services, IConfiguration configuration)
    {
        var openAIOptions = configuration.GetSection("OpenAI").Get<OpenAIOptions>()
            ?? throw new InvalidOperationException("配置中缺少 \"OpenAI\" 节点。");

        services.AddSingleton(openAIOptions);
        services.AddSingleton<IOpenAIService, OpenAIService>();

        return services;
    }
}
```

这里有三个值得关注的设计决策。第一，配置绑定选择直接从 `IConfiguration` 读取，而非使用 `IOptions<T>` 模式。对于基础组件，直接绑定并注册为单例更加简单直接，避免了 `IOptions<T>` 带来的额外抽象层次，同时保留了启动时校验的能力，配置缺失时会立即抛出 `InvalidOperationException`，而不是等到第一次调用时才暴露问题。

第二，`OpenAIOptions` 和 `IOpenAIService` 均注册为单例。`OpenAIOptions` 是纯配置对象，天然适合单例。`OpenAIService` 不持有任何请求级别的状态，所有请求上下文都通过方法参数传递，注册为单例可以减少不必要的对象分配，也与其内部复用 `ChatClient` 连接池的设计保持一致。

第三，`OpenAIClient` 的生命周期由 `OpenAIService` 内部自行管理，不单独注册到 DI 容器。这样可以防止外部代码直接获取 `OpenAIClient` 并绕过封装层使用，确保所有大模型调用都经过统一的日志、重试和异常处理逻辑。

### 四、总结
本文我们从孢子记账微服务架构的实际需求出发，完成了 LLM 调用层的封装设计与实现。

首先，我们审视了不封装直接调用 SDK 的种种弊端——配置散落、代码重复、缺失横切关注点，明确了在微服务架构中将大模型调用能力抽象为统一基础组件的必要性。

然后，基于"面向业务而非面向 SDK"的原则，设计了 `IOpenAIService` 接口和 `OpenAIOptions` 配置模型。接口以 `ChatAsync` / `ChatStreamingAsync` 两组方法覆盖全部调用场景，配置模型则通过 `MaxRetries` 和 `RetryDelayMilliseconds` 将容错能力外化为可调参数。

在实现层面，`OpenAIService` 内置了完整的异常分类处理与指数退避重试机制，`429` 和 `5xx` 错误自动重试，`OperationCanceledException` 直接透传，其他错误立即失败。流式调用采用"先缓冲后输出"策略保证重试语义的正确性。最后通过 `AddOpenAIService` 扩展方法将一切串联到 DI 容器中，做到一行注册、开箱即用。

封装完成之后，任何一个孢子记账的微服务只需在 `Program.cs` 中添加 `builder.Services.AddOpenAIService(builder.Configuration)`，即可通过构造函数注入 `IOpenAIService` 来调用大模型能力。无论是简单的文本补全还是实时流式输出，都只需要调用一个方法。这种体验上的简洁，背后是封装层对配置管理、客户端生命周期、日志记录、异常处理、重试策略等横切关注点的系统性收敛。

当然，这只是一个起点。当前版本的封装层聚焦于对话补全这一核心能力，后续我们将在此基础上逐步扩展嵌入（Embedding）、函数调用（Function Calling）、多模型路由以及 Token 计费等进阶功能，让这层封装真正成为孢子记账智能化能力的坚实底座。从下一篇文章开始，我们将正式进入智能化业务场景的开发——首先从智能账单录入入手，看封装层如何在真实业务中发挥价值。
